# Acceptance Harness — Full Procedure (verified versions: pytest 8.x; IEEE 829-2008; ISTQB CTFL v4.0)
Retrieval date: 2026-10-07. Sources: istqb.org, pytest.org, github.com/actions/upload-artifact, repo AGENTS.md R3 LIVE DIRECTIVES. See references/SOURCES.md for full provenance.

## Step 1 — Enumerate requirements (one scenario per requirement)
Never combine two requirements in one scenario; each scenario maps to exactly one requirement ID from the backlog or spec. Template: `SCENARIO-<ID> | requirement:<req-id> | outcome:PASS|FAIL|BLOCKED`. Failure sign: scenario covers login AND payment — two requirements in one row. Threshold: if a requirement has no scenario, block merge until one is written.

## Step 2 — Write PASS criteria as observable assertions
Criterion must be checkable by a script or human in under 60 seconds. Bad: "the page feels fast". Good: "HTTP 200 within 2s p95 across 5 runs". Bad: "looks correct". Good: "axe zero A/AA violations". Every criterion gets an evidence type: log, screenshot, metric report, or trace pointer. Thresholds for common checks: HTTP response <=500ms p95; axe violations == 0; keyboard reachable <=5 Tab presses; responsive overflow == 0px; selector stability = no nth-child or class-only selectors. Worked example good output: `PASS /login | criterion=HTTP200+p95<=500ms | evidence=tests/e2e/evidence/login.json`. Worked example bad output: `PASS /login` (no criterion). Decision table for outcome selection is in SKILL.md decision table section. Pitfall from research: scenarios without concrete PASS criteria drift into opinion — every scenario needs a checkable assertion with threshold numbers attached. Pitfall from research: evidence not attached to a scenario is unverifiable — pointer must open in under 60 seconds (file path or URL). Pitfall from research: fault injection that crashes the system without recovery is destructive not resilience proof — require recovery and return to PASS after injection stops. Pitfall from research: a scenario that always passes has no discriminating power — add a negative case (wrong input should FAIL).
