# PG RLS Multitenant Skill — Quick Reference (body <500 lines; full procedure in references/pg-rls-procedure.md)
## When to use this skill (trigger) - any of these fires it: - You are adding a new tenant-isolated table or view to an Ottili schema. - A code review mentions "tenant_id", "organization_id", or "namespace" columns without RLS. - A migration adds a column that becomes the tenant discriminator. - An incident report says "user X saw user Y's data". - You are reviewing Supabase, Hasura, Prisma, or direct SQL for missing RLS. ## When NOT to use this skill - Single-tenant databases (no tenant discriminator needed). - Read-only analytics replicas where RLS is enforced upstream. - Tables that intentionally share rows across tenants (e.g., global config) — mark them `bypassrls` explicitly instead of omitting policies. ## Decision table — tenant key strategy | Pattern | When to pick | Pitfall | |---------|-------------|---------| | `tenant_id` column on every row table | Default; works with any ORM | Must be NOT NULL; FK from shared tables | | JWT claim `tenant_id` via `current_setting('app.current_tenant')` | Serverless / connection-pool reuse | Claim must be set per-request, never cached globally | | Security-definer lookup function (`current_tenant()`) | Complex hierarchies (org > team > user) | Function must be IMMUTABLE false; test for SQL injection | ## Numbered procedure (summary; full recipe in references/pg-rls-procedure.md) 1. **Choose tenant key** — column preferred; document the choice in the migration comment. 2. **CREATE POLICY** per role-permission combination; use PERMISSIVE for additive rules, RESTRICTIVE for deny overrides. 3. **ALTER TABLE ... ENABLE ROW LEVEL SECURITY** then **FORCE ROW LEVEL SECURITY** on every non-dev table (dev tables get NO FORCE with a comment). 4. **Grant SELECT only** — never GRANT ALL on RLS-protected tables; service_role bypasses RLS so restrict it in Supabase/Postgres auth layer separately. 5. **Expand/contract migration**: add column → backfill → add policy → verify leak test → contract old data later via separate migration with rollback SQL in same file. 6. **Run leak test harness** (`scripts/pg-rls-leak-test.sh`) against a real Postgres Docker image before merge; expect all PASS or block merge. ## Pitfalls from research (real incidents) - Owner bypasses RLS unless FORCE is set — a table created by a migration role silently exposes rows to that role's sessions ([PostgreSQL docs](references/SOURCES.md#primary-sources)). - Views are security-definer by default and bypass RLS unless `security_invoker = true` ([PostgreSQL docs](references/SOURCES.md#primary-sources)). - Missing GRANT before policy → error 42501 before any policy runs ([Supabase docs](references/SOURCES.md#primary-sources)). - `service_role` key bypasses all RLS — never use it client-side ([Supabase docs](references/SOURCES.md#primary-sources)). - Sub-select race condition between policy evaluation and INSERT can leak rows under concurrent load ([PostgreSQL docs](references/SOURCES.md#primary-sources)). ## Verification checklist (all must pass before merge) [ ] Every row table has at least one policy matching its tenant column [ ] FORCE ROW LEVEL SECURITY is set on all non-dev tables [ ] No GRANT ALL on protected tables [ ] Leak test harness runs green against Docker Postgres [ ] Migration includes rollback SQL [ ] Views use security_invoker = true or are excluded from RLS scope ## Related skills outbox-idempotency problem-json-contracts SKILLEOF
