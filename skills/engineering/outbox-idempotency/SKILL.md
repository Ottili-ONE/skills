# Outbox Idempotency Skill — Quick Reference (body <500 lines; full procedure in references/outbox-procedure.md)
## When to use this skill (trigger) - any of these fires it: - You are adding an event-driven integration (webhooks, CDC, message bus) that must not lose or duplicate events. - A migration introduces an `outbox` table or an `idempotency_key` column. - An incident report says "event delivered twice" or "event never arrived". - Code review mentions `INSERT INTO outbox` without a unique key or replay logic. - You are designing retry semantics for a service that writes events and sends them. ## When NOT to use this skill - Fire-and-forget logging with no consumer expectation of delivery. - Streams where ordering does not matter and duplicates are harmless (e.g., metrics). ## Decision table — idempotency strategy | Pattern | When to pick | Pitfall | |---------|-------------|---------| | UUID v7 idempotency key on every outbox row | Default; sortable by time; collision-safe | Key must be generated BEFORE the business transaction commits | | Natural key (entity_id + version) | Immutable entities with monotonically increasing versions | Version gaps look like missing events if not handled | | Hash of payload + sequence number | High-throughput streams where UUID cost matters | Hash collisions possible; pair with sequence check | ## Numbered procedure (summary; full recipe in references/outbox-procedure.md) 1. **Create outbox table** — `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`, `idempotency_key text NOT NULL UNIQUE`, `payload jsonb NOT NULL`, `created_at timestamptz NOT NULL DEFAULT now()`, `sent_at timestamptz`, `attempts int NOT NULL DEFAULT 0`, `last_error text`. 2. **Write in same TX** — INSERT outbox row + business data in ONE transaction; commit both or neither. 3. **Poller loop** — SELECT ... WHERE sent_at IS NULL ORDER BY created_at LIMIT N FOR UPDATE SKIP LOCKED; publish; UPDATE sent_at = now() on success; increment attempts on failure. 4. **Poison handling** — after max_attempts (default 5), move row to poison_outbox table with error snapshot; do NOT delete it. 5. **Replay** — SELECT from poison_outbox ORDER BY created_at; re-publish only after root cause is fixed; keep original idempotency_key so dedup still works. 6. **Leak test harness** (`scripts/check_outbox.py`) validates schema, unique constraint, poller ordering, poison threshold, and no lost events under concurrent publish. ## Pitfalls from research (real incidents) - Out-of-order delivery when poller uses LIMIT without ORDER BY + SKIP LOCKED ([PostgreSQL docs](references/SOURCES.md#primary-sources)). - Duplicate publishes when poller crashes between publish and UPDATE sent_at ([OutBox pattern literature](references/SOURCES.md#primary-sources)). - Poison messages block the queue when max_attempts is absent ([Kafka docs](references/SOURCES.md#primary-sources)). - Lost events when business TX commits but outbox INSERT fails due to connection drop ([Microservices patterns](references/SOURCES.md#primary-sources)). - Replaying without idempotency_key causes double-delivery even after fix ([OutBox pattern literature](references/SOURCES.md#primary-sources)). ## Verification checklist (all must pass before merge) [ ] Outbox table has UNIQUE idempotency_key [ ] Business write + outbox INSERT are in ONE transaction [ ] Poller uses ORDER BY created_at + FOR UPDATE SKIP LOCKED [ ] Poison threshold moves rows after max_attempts [ ] Replay preserves original idempotency_key [ ] Leak test harness runs green against Docker Postgres [ ] No DELETE on poison_outbox rows
