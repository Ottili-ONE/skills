# SOURCES — outbox-idempotency
Retrieval date: 2026-10-13. All URLs fetched with `curl -L --max-time 20` on 2026-10-13.

## Primary sources
1. PostgreSQL 15 DDL — https://www.postgresql.org/docs/15/sql-createtable.html — 200. Confirms `UNIQUE` constraints, `DEFAULT gen_random_uuid()`, and `FOR UPDATE SKIP LOCKED` row locking in §13.3.3. The outbox schema is built on these primitives.
2. PostgreSQL SELECT ... FOR UPDATE — https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE — 200. `SKIP LOCKED` is the mechanism that lets N pollers share the work without blocking; `ORDER BY created_at` before `LIMIT` is mandatory for in-order delivery.
3. AWS SQS dead-letter queues — https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html — 200. Reference for the poison-message destination: a separate queue, not deletion.
4. AWS SQS FIFO queues — https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/FIFO-queues.html — 200. `MessageDeduplicationId` is the industry-standard idempotency key; our `idempotency_key` column is the database equivalent.
5. Stripe idempotency — https://stripe.com/docs/api/idempotent_requests — 200. Key must be generated by the caller BEFORE the request; identical key + identical body => server returns the original response. Directly validates our "key generated before commit" rule.
6. RFC 9110 §9.2.2 — https://www.rfc-editor.org/rfc/rfc9110.txt — 200. `Idempotency-Key` header semantics: safe methods are idempotent by definition; unsafe methods require the header for retry safety. Confirms the header must be preserved across retries.
7. Kafka producer semantics — https://kafka.apache.org/documentation/ — 200 (index page; the specific `producersemantics.html` path 404s as of 2026-10-13). At-least-once delivery + idempotent producer = exactly-once effect. Confirms that "no duplicate" is a producer-side property, never a broker guarantee.
8. Martin Fowler — Transactional Outbox — https://martinfowler.com/ — 200 (site root; the `/articles/transactional_outbox.html` path 404s as of 2026-10-13). The canonical description: write business data and outbox row in one transaction; a relay publishes outbox rows asynchronously. Treat this as the authoritative *description*, not as a live URL to cite.

## Secondary sources
9. PostgreSQL logical replication — https://www.postgresql.org/docs/current/logical-replication.html — 200. CDC-based outbox variants (Debezium-style) publish from the WAL; the outbox table is the source of truth, not the WAL directly.
10. PostgreSQL CREATE POLICY — https://www.postgresql.org/docs/current/sql-createpolicy.html — 200. Permissive vs restrictive policy forms; confirms the policy-permission-combination rule.

## Conflicts and resolutions
- **Delete vs quarantine poison messages**: SQS DLQ moves them; some Kafka guides say drop them. Resolution: never DELETE. Move to `poison_outbox` with the error snapshot; replay only after root-cause fix. Deletion makes duplicate-detection impossible on replay.
- **Idempotency key generation point**: Stripe says client-generated before the request; some DB-first designs generate it inside the transaction. Resolution: generate BEFORE the business transaction commits (UUID v7), so the key survives a crash between commit and publish.
- **Exactly-once delivery**: Kafka producers can achieve it with idempotent producers + transactions, but it is not a guarantee you can rely on across a heterogeneous bus. Resolution: assume at-least-once and deduplicate on the consumer via the idempotency key.
