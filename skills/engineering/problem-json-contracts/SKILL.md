# Problem JSON Contracts Skill — Quick Reference (body <500 lines; full procedure in references/problem-procedure.md)
## When to use this skill (trigger) - any of these fires it: - You are designing an HTTP API endpoint that returns errors. - A migration adds a new error code or changes a field name in an error response. - An incident report says "client cannot parse the error" or "retry loop hammered us". - Code review mentions `{"error": "..."}` without type/instance/status fields. - You are adding a new language SDK and need stable error shapes. ## When NOT to use this skill - Internal CLI-only tools with no HTTP transport. - Health-check endpoints that return plain text 200. ## Decision table — error shape | Pattern | When to pick | Pitfall | |---------|-------------|---------| | RFC 9457 `application/problem+json` with type URI | Default for all public HTTP APIs | `type` must be an absolute URI; use `about:` or `urn:` for internal codes | | Versioned JSON Schema (`$id` with version path) | Multiple client versions in the wild | Never break existing `$id`; add new schema version instead | | Error catalogue enum (machine code + human message) | Every error must be machine-searchable by ops | Do not put stack traces in the catalogue response; log separately ## Numbered procedure (summary; full recipe in references/problem-procedure.md) 1. **Pick type URI** — `about:<product>:<domain>:<code>` for internal; `https://api.ottili.dev/problems/<code>` for public. Never reuse a type for two different semantics. 2. **Required fields**: `type`, `title`, `status` (int), `detail`, `instance` (URI). Optional: `trace_id`, `retry_after`, `errors` (field-level array). All strings UTF-8, max lengths enforced by schema (`title` <= 120, `detail` <= 500). 3. **Status code mapping**: 4xx = client fault with fix hint; 5xx = server fault with trace_id only; never leak internals on 5xx. Map exactly one status per type — no overlap between catalogue entries. 4. **Retry semantics**: include `retry_after` (seconds) on 429/503; idempotency-key header preserved across retries; client MUST back off exponentially starting at 1s, cap at 60s, max 5 attempts then surface to user with instance URI for support lookup. 5. **Error catalogue**: single YAML file listing every code, its status, title template, and retryability flag; CI runs the validator against it so no duplicate codes and every code has a schema entry matching the catalogue enum value exactly one-to-one between OpenAPI operation responses and catalogue entries via script (`scripts/check_problem_catalogue.py`) which fails CI on mismatch or missing entries ## Verification checklist (all must pass before merge) [ ] Every endpoint returns application/problem+json on >=400 [ ] Catalogue YAML has no duplicate codes [ ] Schema validates all examples in references/examples/ [ ] Retry-after present on all retriable errors [ ] No internal fields leaked on 5xx responses [ ] scripts/check_problem_catalogue.py passes in CI ## Related skills pg-rls-multitenant outbox-idempotency
